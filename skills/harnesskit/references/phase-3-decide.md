# Phase 3: decide the target

Use the canonical layout, decision log, capability matrix, policy matrix, and model roster templates.

Choose which facts are global, scoped, profile-specific, or tool-specific. Keep scope facts near the code/records they govern. Treat a scope file as metadata unless an adapter explicitly loads it.

Choose account rules from owner-confirmed identities. Distinguish provider login, connector account, Git author, Git remote identity, and publishing destination. Record the permitted data flow for each capability.

Choose model classes by task: quick bounded work, routine implementation, difficult review, or another owner-defined class. Record provider-specific current model identifiers only after a current check. Do not publish private account labels, assume aliases are stable, or infer quality from price alone. Keep the original run's model choices out of the kit.

Choose active skills separately from a parked library. Preserve provenance, licenses, and installation locks. Retain valued features even if the measured sample shows no use.

Choose copy, import wrapper, or link by consumer behavior. Prefer generated copies when a tool may replace a file atomically. Avoid hardlinks; inode replacement can silently detach them.

Choose external isolation for mandatory secrets and scope restrictions. A local broker wrapper is a temporary convenience, not a complete boundary.

Gate: the owner approves the concrete layout, scope/account matrix, model classes, preservation plan, and named enforcement gaps.
