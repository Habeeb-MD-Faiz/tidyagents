# Principles

| Rule | Why |
|---|---|
| Start with owner intent | A tidy tree can still serve the wrong workflow |
| Separate policy, scope, profile, and capability | An account name does not determine data ownership |
| Keep one canonical editable source per fact | Copies drift unless generated and checked |
| Keep tool adapters small | Vendor discovery and precedence differ |
| Keep user-specific values in private records | The shareable kit must not identify its source |
| Prefer evidence over a remembered report | Settings and tool versions change |
| Measure loading and use separately | Presence is not execution, and silence is not uselessness |
| Preserve every original and history | Dedupe can erase context that counts do not reveal |
| Review the exact mutation plan | A goal is not permission for every implementation |
| Use external boundaries for mandatory isolation | Same-user instructions and hooks can be bypassed |
| Treat archived rules as data | Old instructions must not become current authority |
| Make a small reversible pilot first | One bad adapter should not affect all tools |
| Keep a tested restore route | Backup existence does not prove recovery |
| Report limitations beside results | A green file check is not a tested runtime |

Portable means shared intent plus declared adapters. It does not mean identical configuration syntax, identical privileges, or one universal prompt.

Keep the core instructions short. Store detailed procedures in skills, optional material in a library, and third-party components with provenance and licenses. Do not silently rewrite installed packages.
